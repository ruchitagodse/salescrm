# Data conventions
Status: Approved | Last updated: 2026-11-26

- UUID primary keys on every table.
- `created_at` and `updated_at` on every table.
- All timestamps use PostgreSQL `timestamptz`.
- Money is INR only, stored as integer paise in PostgreSQL bigint. Use Drizzle bigint mode `bigint` and JavaScript bigint for exact arithmetic; never floats. Number.MAX_SAFE_INTEGER is 9,007,199,254,740,991 paise, but this implementation never converts money to number. PostgreSQL signed bigint range is -9,223,372,036,854,775,808 through 9,223,372,036,854,775,807 paise. Serialize bigint as decimal strings at JSON boundaries.
- Table and column names use snake_case; table names are plural.
- Enable RLS on every application table with no public policies. All business access runs through authorized server code and Drizzle.
- Do not introduce tenant or organization IDs.
- Business tables get nullable `deleted_at timestamptz`; default queries must exclude deleted rows. Retention/restore semantics remain open. Profiles are an identity foundation table, not a business table, and follow auth.users deletion by cascade.
- Shared PostgreSQL `set_updated_at()` trigger function maintains updated_at; attach a trigger to each table in its migration.
- Phase 2 implements only profiles. Its UUID id references auth.users(id) with ON DELETE CASCADE; full_name is nullable, with created_at/updated_at. auth.users is referenced via pgSchema("auth") but excluded from managed migration exports.
- Profile creation uses an on-first-authenticated-request upsert, `ON CONFLICT DO NOTHING`: handles existing dashboard-created accounts without installing a trigger on Supabase-managed auth.users. It never overwrites an existing profile. Until a user accesses OS, their profile need not exist.

## Open questions
- Soft-delete retention, restore semantics and deleted-row uniqueness rules.
- Required uniqueness, indexes, referential actions and business constraints in each phase.

## Approved Phase 3A decisions (2026-11-24)
- Value sets use text columns with CHECK constraints generated from single exported TypeScript const arrays in src/lib/lead-values.ts; the same arrays drive Zod and future UI. No native PostgreSQL enums.
- Business UUIDs default to PostgreSQL gen_random_uuid() via the shared id helper's .defaultRandom(); explicit app-generated UUIDs remain supported, while profiles.id has no default and must match auth.users.id. Shared timestamp/soft-delete helpers, per-table set_updated_at() triggers and RLS without policies still apply.
- Company has many contacts; company_id is optional. Contact has many leads; contact_id is required. Foreign keys use ON DELETE RESTRICT: hard deletes must not orphan children. Soft deletion does not cascade; reads exclude the queried entity's deleted rows. Existing child records retain their FK when a parent is soft-deleted. New/changed parent links require a non-deleted parent. Broader parent deletion/restore UX remains open.
- Sources: instagram, whatsapp, meta_ads, website, referral, cold_outreach, other. Statuses: new, contacted, qualified, converted, lost; default new. Lost requires nonblank lost_reason in validation and a DB CHECK. converted_at is server-maintained when entering converted (retained on other transitions, refreshed when entering converted again). Converted is status-only until Phase 4.
- Approved Phase 3A revision: entry_method uses the shared const values manual/integration with a text CHECK and default manual; source_detail is nullable plain text for campaign/ad/form details. Source describes origin independently of entry method. Phase 3 supports manual entry; Phase 8 adds Meta ads, Instagram and WhatsApp intake. Phase 8 standard provider attribution is specified below; custom campaign/form-answer mapping remains open.
- Contact phone/email normalized values are stored. E.164 normalization uses libphonenumber-js with default IN; email trims and lowercases. Blank optional strings become null. A contact needs phone, email or instagram_handle. Partial unique phone/email normalized indexes apply only to live rows and non-null values.
- New enquiries match live contacts by normalized phone OR email; reuse the contact and fill only empty fields, never overwrite existing values. Two different contacts matching the two keys is an unresolved identity conflict: fail atomically rather than choose or merge them. Transactions and sorted transaction-scoped advisory locks coordinate identity writes; partial unique indexes are the final race guard.
- Company case-insensitive name duplicates produce a warning, not a block. No ownership/assignment fields, activities or note entities; notes remain plain text.
- budget_paise uses bigint internally, accepts bigint or decimal integer strings (never numbers), and is returned as a decimal string in lead DTOs. Validate signed PostgreSQL bigint bounds; no float conversion.
- Node's built-in test runner tests pure normalizers and merge decisions using Node 24 TypeScript stripping. Zod schemas are shared with future server actions. No Phase 3A UI/routes or migration generation/application.

### Remaining open questions
- Merging two existing contacts and resolving split phone/email matches.
- Soft-deleted parent/child restore workflows; deleted-row uniqueness collisions on restore.
- Negative-budget business rules and transition restrictions beyond the supplied status rules.

## Approved Phase 4 defaults (2026-11-25)
Ruchita approved Discovery -> Proposal -> Negotiation stages, separate open/won/lost deal outcomes, explicit Convert to deal, at most one deal per lead, and title, linked lead/contact, stage, INR value, expected close date, loss reason and notes. Activities remain Phase 5.

Implementation conventions: pipeline_stages is seeded with the three fixed stages; no stage administration is added. Deals require a title and lead; contact is derived through the lead rather than duplicated. Lead IDs have an unconditional unique constraint in deals, including deleted deals, so deletion cannot bypass the one-deal rule. Conversion locks the live lead, creates the deal and marks the lead converted in one transaction; repeated conversion returns the existing live deal. An archived deal blocks reconversion. Stage/outcome text CHECKs use exported const arrays. Stage and lead FKs use RESTRICT. Standard UUID defaults, timestamps, soft deletion, RLS/no policies and updated_at triggers apply to both new tables.

Deal value is nullable non-negative bigint paise, serialized as a decimal string; expected close is a nullable date. Lost outcome requires a nonblank loss reason. Edits do not rewrite the lead conversion timestamp or change deal identity. Moves between the three fixed stages do not imply won/lost outcomes. No additional transition restrictions are imposed in this phase; configurable stages, reopening/closing policy and stage history remain open questions.

## Approved Phase 7 defaults (2026-11-26)
Phase 7 defaults Approved on 2026-11-26: date-filtered metrics use inclusive India calendar dates, translated to [start, next-day-end) instants for created_at and direct inclusive dates for paid_on/spent_on. Current month to date is the default; custom ranges are limited to 3,660 days between endpoints to bound report size. Cash receipts/expenses include only recorded, non-deleted rows; net cash is receipts minus expenses, not profit/accrual revenue. Booked order value uses header total once per order created in range. Lead-to-deal conversion uses non-deleted leads created in range and their non-deleted linked deals, preventing cross-cohort rates above 100%. Deal stage/outcome breakdowns use deals created in range and current stage/outcome, not a claim about when they moved or closed. Outstanding balances and open pipeline are current all-time snapshots, separately labeled. Voids retroactively revise cash-date totals based on current valid rows; no historical as-of reconstruction. Money sums use bigint/numeric-text -> bigint -> decimal-string DTOs, never Number money arithmetic. Chart coordinates may use bounded normalized integer ratios computed in bigint; labels/tables/tooltips retain exact amounts. Read-only repeatable-read snapshots prevent mixed totals within a report. No Phase 8/AI/forecasting or new business tables.

## Approved Phase 6 defaults (2026-11-25)
Phase 6 Approved on 2026-11-25: quote/order item amounts and totals, payments and expenses use bigint INR paise only. Positive whole quantities; unit prices may be zero; receipts/expenses must be positive. Totals are checked for signed bigint overflow and calculated server-side, never accepted from clients. GST/discount fields and calculations are absent. Sequence-backed Q-/O- references are global technical references with a minimum six-digit display, not fiscal invoice numbers; gaps are allowed. UUID primary keys remain authoritative.

Quotation transitions: draft -> sent -> accepted/rejected, rejected -> draft; only drafts can edit title/lines. Accepted quotes convert explicitly and transactionally to one immutable order with copied items and customer name. Unconditional quotation uniqueness prevents a second order even after archival. Payments lock their order before summing recorded, non-deleted receipts and inserting; voiding uses the same lock. No recorded payment/expense amount edits or silent deletion: status recorded/voided, voided_at and a required void_reason retain history. Draft quotation deletion is soft only. Standard columns, RLS/no policies, RESTRICT FKs and updated_at triggers apply to all six document/item/receipt/cost tables.

## Approved Phase 5 defaults (2026-11-25)
Activity types call/meeting/task/follow_up and statuses planned/completed/cancelled use shared exported const arrays for DB CHECKs and UI/Zod. Exactly one nullable FK among contact_id/lead_id/deal_id must be set (DB CHECK); FKs RESTRICT. Required due_at uses timestamptz; UI datetime-local values are interpreted explicitly as Asia/Kolkata (+05:30), never the browser/server local timezone. Today is the India calendar day, Upcoming starts at tomorrow India midnight, Overdue means planned and due_at < now; Today can overlap Overdue. Completed view uses completed status. Completion timestamp is set only on entering completed, preserved on completed edits and cleared on reopening/cancelling; a CHECK keeps timestamp/status consistent. Default activity lists exclude deleted rows; parent soft deletion does not cascade. Title must be nonblank; new/changed target links require a live parent. Standard UUID/defaults/timestamps/RLS/no policies/update trigger apply. Types, statuses and links are fixed; automated notifications, recurrence and assignment are out of scope.

## Approved Phase 8 intake defaults (2026-11-26)
Ruchita selected automatic lead creation from first inbound messages. Meta lead forms create one lead per provider lead ID; Instagram/WhatsApp create one lead per channel + business account + sender identity, with subsequent messages linked to the same lead. Inbound only; no outbound sends or historical import in this phase. Provider event IDs are durable unique replay keys scoped by channel/account; a successful event marker and lead/contact/identity writes must commit atomically. Business soft deletion must never make an old provider event eligible for re-creation. Existing phone/email fill-only matching and split-identity conflicts remain unchanged; Instagram scoped IDs are never fabricated into usernames or phone numbers. Invalid/unresolvable identities remain reviewable rather than guessed. Conversion begins at source instagram/whatsapp/meta_ads with entry_method=integration; provider attribution stays separate from editable source_detail. No automatic follow-up/activity creation, merging of existing contacts, attachment downloads or AI parsing. Retention and consent/erasure workflows remain open.

## Approved Phase 9 analyst defaults (2026-11-26)
Ruchita approved on-demand Gemini reports using aggregate analytics only, observations and suggested actions, without automatic CRM changes, chat history or scheduled reports. Reuse Phase 7 India date/cohort/cash/current-snapshot semantics; cash is not profit/accrual revenue, and outcome counts are not period win timestamps. Explicitly construct an allowlisted aggregate snapshot: exact paise/count decimal strings and fixed categorical labels only; no record identifiers/names/contact details/messages/notes/custom text or outstanding-order rows. No record-level context is sent. AI output is advisory, structured and bounded; evidence IDs must refer to facts in that request. These checks do not establish semantic correctness. Money stays bigint/decimal strings; AI prose never becomes authoritative ledger data. No report persistence, business mutation, tool execution, web grounding, history or Phase 10 work.

## Approved quotation enhancement revision (2026-11-26)
Ruchita approved fixed INR tax and discount amounts, not percentage/GST-rate calculations: total = item subtotal - discount + tax; discount cannot exceed subtotal; all values remain bigint paise. Nonempty configured payment milestone amounts must sum exactly to final total; quantities remain whole positive integers. Add description, validity and payment terms. Existing quotations/orders retain zero adjustments and original totals; accepted-order snapshots retain adjustments explicitly. Requested statuses now include expired. Existing historical manually-Sent records remain historical, not retroactively reclassified as provider deliveries. Generated PDFs are immutable versioned snapshots with a hash and stored bytes; sent content cannot be overwritten. Revisions require a new draft version/quotation preserving the previously sent record. Status and sending history are append-only. Gmail SMTP selected; no credentials from chat are copied. Unverified public address/phone/email are omitted until configured/confirmed; brand PROSPERA Digital Solutions and sign-off Ruchita Godse are supplied. ## Approved dashboard phase definitions (2026-11-26)
Ruchita approved month-to-date/default and custom inclusive India dates, recorded cash/expenses/net cash (not accounting profit), and quotation counts/value covering each non-deleted quotation record created in range, explicitly including revised drafts as separate documents. PDF versions never multiply quote counts/values. Existing Phase 7 lead/deal creation cohorts and separately labeled current all-time balances/pipeline remain authoritative. Deal average uses known values only, rounded half-up to the nearest paise with bigint; display unknown-value count and no average when none are valued. Deal win share is current won/(won+lost) for deals created in range, not a monthly closure rate.

Current follow-up counts cover planned follow_up activities: Today uses the India calendar day, Upcoming starts tomorrow and Overdue means due_at < snapshot now, so Today can overlap Overdue. Completed activities cover all completed non-deleted types by completed_at in the selected period; reopening removes them from this current-state report. Open deals past expected_close_date and quotations still Sent/within validity are current attention queues, capped in the UI with totals visible. Source cash uses recorded non-deleted payments dated in range, attributed through their current live order -> quotation -> lead/deal -> lead source; amounts with unavailable/archived lineage stay in an explicit Unattributed bucket. This is current-source attribution, not acquisition ROI or immutable campaign history. New leads mean still marked new, not proof that no contact occurred. Unsupported accounting profit, actual monthly closure dates, service revenue and reliable last-contact age remain unavailable rather than zero/inferred. Dashboard insights are deterministic facts with an explicit on-demand AI Analyst link; visiting the dashboard does not call Gemini or send messages. No dummy/seeded production metrics or schema changes.
