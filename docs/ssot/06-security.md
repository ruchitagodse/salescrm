## Approved Phase 3A access boundary (2026-11-24)
Approved revision: business data functions accept plain inputs and perform no session/authentication checks themselves. They remain guarded by import "server-only" and expose no routes/actions. Callers establish trust first: Phase 3B server actions call the existing requireUser()/getUser() helper; Phase 8 webhooks verify provider signatures/tokens before processing. createLeadWithContact takes plain input for reuse from both entrypoints without a browser session. Database initialization remains lazy. A server-only import is a bundle boundary, not authorization. All authenticated users retain equal access; no ownership/role field is added. This supersedes the opaque-context design.

Input is validated with shared strict Zod schemas. Caller-supplied normalized fields, timestamps and deletion flags are rejected. Parameterized queries handle input; only fixed value-set constants enter SQL CHECK literals. All default entity reads/lists/updates exclude deleted rows. Raw database errors and their causes never leave the data layer. Deadlocks/serialization failures return a retryable generic error; identity conflicts and uniqueness failures have safe typed error codes. No service-role Auth key is introduced.

## Phase 8 webhook boundary (2026-11-26)
Only the three exact /api/webhooks/meta-ads, /api/webhooks/instagram and /api/webhooks/whatsapp paths bypass Supabase session redirects. GET verification uses the configured verification token; POST authenticates the exact bounded raw request body using HMAC-SHA256 and constant-time comparison before JSON parsing, Graph calls or DB writes. Each route has a server-only app secret and explicit configured business-account allowlist (one account per channel initially). Signatures have no inherent freshness guarantee; unconditional provider event keys make replays idempotent. Echo/status/read receipts are ignored. No access tokens in Graph query strings/logs; provider-required callback verification queries must not be logged or shared. Graph requests use Authorization headers with timeouts, no redirects and no caching. Webhook failures return generic messages; event review is authenticated and exposes only normalized inbound content/safe codes. All authenticated users retain equal access. App review/permissions, HTTPS callback registration and credential rotation remain operational prerequisites, not claimed completed.

## Phase 9 Gemini boundary (2026-11-26)
Authenticated /analyst and its generation server action independently call requireUser/getUser before any snapshot or provider operation. The browser submits only validated dates/focus, never an API key, model prompt, arbitrary endpoint or client-built context. Server constructs an allowlisted aggregate-only payload; free-form business content and record identifiers are excluded. Gemini key is server-only, passed in a header to a fixed HTTPS endpoint; requests have a timeout, body/output bounds, no redirects, cache or automatic retries. Responses are schema/evidence-validated and rendered as escaped text, never HTML/Markdown commands or executable tools. Failures are generic and do not log prompts, model output, credentials or provider error bodies. The explicit Generate with Gemini submission sends business aggregates to Google; no background call on page render. All authenticated users have equal analyst access. A bounded process-local per-user cooldown/single-flight guard limits repeats; it is not distributed quota enforcement. Provider billing/quota, data terms/retention and model availability require owner configuration/verification.

## Workflow/document enhancement boundary (2026-11-26)
Quotation PDFs, snapshots, history and delivery records remain private through authenticated server routes/actions and Drizzle/RLS without public policies. Stored PDF versions are immutable; signed-in preview/download uses private no-store responses. SMTP credentials and WhatsApp access token stay server-only; no test email or WhatsApp message is sent by the agent. External sends require an explicit recipient/channel selection in the app. Provider submission acceptance alone can mark Sent; delivered/read require separate authenticated provider status evidence. Ambiguous SMTP/WhatsApp timeout is recorded as unknown, not retried automatically or labeled failed/delivered; duplicate-click protection must preserve the same attempt identity. Provider raw error bodies/SMTP credentials are never exposed. Existing inbound-only integration behavior remains until outbound quotation sending is explicitly configured. Runtime Auth fetch/response deadlines and transaction-local DB/lock timeouts must not race non-idempotent writes and claim cancellation.
